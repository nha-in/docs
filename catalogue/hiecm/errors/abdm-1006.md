## In plain words

ABDM-1006 says the request did not pass validation, and the message says
which rule. It is the same code for a wrong HI type, a wrong count, an
unreadable body and a value that decrypted to nonsense, so the message
is the diagnosis, not the code. The code often arrives as
`ABDM-1006: ` with a trailing colon and space. See
[error body shapes](hiecm.concept.error-body-shapes).

## Before you start

Have the raw response body and the exact request you sent, including
which certificate you encrypted with.

## What happens

The messages, and what each one means:

| Message | Cause | Fix |
|---|---|---|
| `Invalid mobile number` or `Invalid Mobile Number` on a number you know is right | The field was encrypted with the other RSA key, so it decrypted to garbage | Use the PHR key for `/v3/phr/*` and the profile key elsewhere. See [the two public keys](hiecm.concept.two-public-keys) |
| `Bad Request, invalid request Body` | The JSON did not parse or a required field is missing | Validate the body against the specification; a trailing comma in an array is enough |
| `415 UNSUPPORTED_MEDIA_TYPE ...` | No `Content-Type: application/json` header | Add the header |
| `No care context linked with given reference number`, on the notify acknowledgement | The context notify ran ahead of the link | Retry at 5, 15 and 60 seconds. See [context notify timing](hiecm.concept.context-notify-timing) |
| `Invalid HIType, it must be in ...` | `hiType` outside the published list | Use one of the listed values |
| `Invalid count, must be 2 digit and ranges between 1 to 20` | `count` outside 1 to 20 | Fix the count |

## How you know it worked

The original call returns its normal result: a `txnId` from the OTP
request, a 202 from consent init, a `SUCCESS` acknowledgement on the
notify callback.

## When it goes wrong

The message is not in the table. Read it literally; it names the field
or the rule. If it names a field you did not send, the body is being
read as the wrong type, which is the `Content-Type` case.
