The drop's 28 operations split across `hiecm-m3.yaml` (this file, the HIU

handed to whoever owns `hiecm-m2.yaml`, per the diff report's own inventory.

## Applied, HIGH confidence

### 1. Headers attached to all 6 M3 path operations

None of the six referenced `RequestId`, `Timestamp` or `CmId` before this
pass, even though `components/parameters` already defined them. A new
`HiuId` parameter (`X-HIU-ID`) is added, matching the existing `CmId`
shape, and each path now carries the subset the drop requires:

- `m3_consent_request_init`: REQUEST-ID, TIMESTAMP, X-CM-ID
- `m3_consent_request_status`: REQUEST-ID, TIMESTAMP, X-CM-ID, X-HIU-ID
- `m3_consent_hiu_on_notify`: REQUEST-ID, TIMESTAMP, X-CM-ID
- `m3_consent_fetch`: REQUEST-ID, TIMESTAMP, X-CM-ID, X-HIU-ID
- `m3_hiu_health_information_request`: REQUEST-ID, TIMESTAMP, X-CM-ID, X-HIU-ID
- `m3_hiu_data_flow_notify`: REQUEST-ID, TIMESTAMP, X-CM-ID

Each header set is read directly off the drop's own `parameters` block for
the matching operation, not inferred.

### 2. `sessionStatus` enum, `TRANSFERRED` moved to the HIP side

`DataFlowNotifyRequest.notification.statusNotification.sessionStatus` said
`[TRANSFERRED, FAILED]`. The drop's own description is explicit: "HIP on
the transfer of data would send sessionStatus - one of [TRANSFERRED,
FAILED]... HIU on receipt of data would send sessionStatus - one of
[RECEIVED, FAILED]." `m3_hiu_data_flow_notify` is the HIU side, so the
enum is corrected to `[RECEIVED, FAILED]`. Both worked examples
(`success`, `partial_failure`) used `sessionStatus: TRANSFERRED` for a
`notifier.type: HIU` payload; the `success` example is corrected to
`RECEIVED`. The operation description's bullet list is corrected to match.
This is the HIP-side value on an HIU-side field, wrong in every place it
appeared in this file, not a one-off typo.

### 3. All 6 webhook response codes, `202` corrected to `200`

`m3_on_consent_request_init`, `m3_on_consent_request_notify_hiu`,
`m3_on_consent_request_notify_hip`, `m3_on_consent_fetch`,
`m3_on_health_information_request` and `m3_on_consent_request_status` all
said `202`. Every one of the drop's six matching operations expects `200
OK` back from the bridge that hosts the callback, without exception. The
drop's own outbound paths, by contrast, consistently return `202`, so this
file had the two directions' status codes reversed. Descriptions are
updated to say 200 and to note the correction; wording that referred to
"a 202 carrying the wrong body" is corrected to "a 200."

### 4. `m3_on_consent_request_notify_hip` requestBody, previously empty

This webhook had a path and a response description only, no schema at
all, the one gap in what this file's own `info.description` otherwise
calls "both halves of the asynchronous exchange." The drop closes it. Its
own `status` enum is wider than its own prose (`[GRANTED, EXPIRED, DENIED,
REQUESTED, REVOKED]` against prose that says "Only GRANTED, REVOKED and
EXPIRED... will be sent to HIP"); the narrower, documented three values
are kept rather than the wider literal enum, and the schema description
says why. `consentDetail` is modeled on the same shape already used
inline for `m3_on_consent_fetch`'s `consent.consentDetail`, since that is
this file's own established pattern for this object rather than a
cross-reference. Two fields are new to this file: `consentId` at the top
level of the notification (previously only inside `consentDetail`), and
`grantAcknowledgement`, a boolean the drop requires and marks with the
generic Swagger-tooling placeholder UUID example
(`3fa85f64-5717-4562-b3fc-2c963f66afa6`) rather than a captured value,
noted in this file as weaker evidence than the drop's other UUID examples.

### 5. New webhook, `/health-information/transfer`

The drop's own description states this "is directly called by HIP Data
Bridge and is not mediated via CM, and hence not routed through the
Gateway," and "should be implemented at HIU side." Modeled as a webhook
payload backfill in this file, per this repo's rule that a callback leg
the drop shows as a path becomes a webhook in ours, never a path of our
own; `operationId: m3_on_health_information_transfer`. Full schema from
the drop: `pageNumber`, `pageCount`, `transactionId`, `entries[]`
(`content`, `media`, `checksum`, `careContextReference`), `keyMaterial`
(reusing the existing `ECDHKeyMaterial` schema, which already matches).

This belongs in M3, not M2, despite the drop tagging the source operation
`consent-management-data-flow-hip`: the tag reflects who calls it, not who
hosts it. It is hosted by the HIU, the actor this file documents, it
bypasses the Gateway entirely (unlike every M2 webhook, which
`hiecm-m2.yaml`'s own description defines as what the gateway posts to a
registered URL), and `m3_hiu_health_information_request`'s own
description already narrates this exact exchange without ever giving it a
schema. `hiecm-m2.yaml` carries a same-concept placeholder,
`m2_on_data_notification`, at a different literal path
(`/api-hiu/data/notification`) with no schema. Flagged here, for
whoever owns `hiecm-m2.yaml`, as very likely the same endpoint, now
superseded by this file's schema; not touched in that file by this pass.

### 6. `ErrorResponse.code`, `integer` corrected to `string`

Every example value in the drop's error schema (`ABDM-1006`, `900901`,
`404`) is a string, matching the drop's own pattern,
`^(ABDM-\d{4}|\d{3,6})(: )?$`, and matching every code in this file's own
`x-abdm-errors` table (`ABDM-1000` and so on). `type: integer` could not
represent any of them. The pattern is added to the schema; same finding
as the sibling M2 report, confirmed independently here.

### 7. `HIType` enum, `Invoice` added

Now 8 values, not 7. Confirmed identically across every `hiTypes`
occurrence checked in the drop, and already present, unnoticed, in this
file's own `x-abdm-errors` table, `ABDM-1006`'s message text, which has
always listed the same 8 names. `HIType` was the one place still pinned
to 7. See `PENDING.md`, P2, below.

## Applied, MEDIUM confidence

### 8. Status enums added to two webhooks

`m3_on_consent_request_status`'s `consentRequest.status` gets
`[REQUESTED, DENIED, EXPIRED, REVOKED]`; `GRANTED` is deliberately absent,
per the drop's own text, since a grant arrives through the notify
callback with `consentArtefacts`, not through this status callback. The
operation description now says so.
`m3_on_consent_fetch`'s `consent.status` gets `[GRANTED, DENIED, REVOKED,
EXPIRED]`, matching what `ConsentFetchResponse.consent.status` already
independently listed in this file, same 4 values.

### 9. `name` and `type` added to `ConsentInitRequest`'s `hip` and `hiu`

Both objects previously required only `id`. The drop requires `id` and
`name` on both and additionally defines, not requires, a `type` field on
both. Corrected to match.

### 10. `reason` field added to `m3_on_consent_request_notify_hiu`

The drop's `notification` object requires `reason` (nullable, example
`null`), carried on a denial. This file had no such field. Added and
marked required, matching the drop.

### 11. New path, health information request status lookup

`GET /hiecm/data-flow/v3/health-information/request/status/{transaction-id}`,
`operationId: m3_health_information_request_status`, a genuine new
operation per the drop's `abdm-data-flow 9`. A pollable alternative to the
`m3_hiu_data_flow_notify` push; nothing in this file covered it before.
Headers: REQUEST-ID, TIMESTAMP, X-CM-ID (no X-HIU-ID; the drop does not
require it here). Response body `{transactionId, status}`; `status` is
left unconstrained, since the drop's own example (`TRANSFERRED`) is the
HIP-side session status value and this operation does not otherwise
define the set.

### 12. Production server added

`https://apis.abdm.gov.in/api` added to `servers`, alongside the existing
sandbox and HSP Registry entries. The drop cleanly separates Sandbox and
Production; this file previously had no production entry for the M3
paths.

## Deferred

### 13. `format: uuid` restoration (report item 8, MEDIUM)

**Not applied.** `consentId`, `consentRequestId` and `id`'s `format: uuid`
was removed under correction C3, because NHA's examples at the time were
not UUID-shaped. This drop's evidence points the other way: `format: uuid`
with a well-formed UUID example at nearly every site checked
(`m3_on_consent_request_init`, `m3_consent_request_status`,
`m3_on_consent_request_status`, `m3_on_consent_request_notify_hiu`,
`m3_on_consent_fetch`, `m3_hiu_data_flow_notify`), with one exception: the
`grantAcknowledgement` example's neighbor, `consentId` in the
`hip/on-notify` operation, uses the generic Swagger-tooling placeholder
UUID (`3fa85f64-5717-4562-b3fc-2c963f66afa6`) rather than a captured
value, so this is evidence, not proof. This matter is settled for this
repository by correction C3 and this pass does not regress it: no
`format: uuid` was added or removed anywhere in this file as a result of
this drop. `PENDING.md`, P1, already prescribes the settling step, one
real sandbox response; the balance of evidence has shifted enough that
whoever owns P1 should read this note and consider running that call.

### 14. `403`, `404`, `500`, `503` response entries (report item 14, MEDIUM)

**Not applied.** The drop declares these near-identically across all 6
path operations and all 6 webhooks it matches; this file's path
operations currently carry `400`/`401` only (`404` also on
`m3_consent_fetch`), and its webhooks carry no error responses at all.
Bolting the drop's error shapes onto the six path operations without also
deciding what a webhook error response even means in this file (the
webhooks model what the gateway sends us, not what we return beyond the
`200`/`202` acknowledgement) would leave the response set half-modeled in
a way that reads as more complete than it is. Left for a dedicated pass
that settles the webhook side of the question rather than a bolt-on here.

### 15. `purpose.code`, `PATRQST` vs the drop's `PATRQT` (report item 15, LOW)

**Not applied.** The drop's own value, `PATRQT`, appears identically in
every one of the three places the M3 enum occurs. This file's `PATRQST`
could be the correct value and the drop could be the typo, or the other
way around; the diff report has no independent way to tell which, and
recommends verifying against a live sandbox consent request before
touching the enum. Left as `PATRQST`.

### 16. `purpose.text` as an enum, `purpose.refUri` required (report item 16, LOW)

**Not applied.** Cosmetic tightening of what a caller may send, with no
observed failure mode motivating it, per the report's own reasoning.

### 17. `permission.frequency.value`/`.repeats`, `number`/`int32` vs `integer` (report item 17, LOW)

**Not applied.** No behavioral difference; both round-trip the same
values.

### 18. Three items for a report back to NHA, not for this file (report item 18, LOW)

The drop's own `hiRequest` required-field list names `nonce` at a level
where it is never defined; this file's nesting under `keyMaterial.nonce`
is already correct. The drop's `identifier.value`/`identifier.type`
descriptions are swapped ("type of identification" on `value`, "the
identification value" on `type`). Both, along with the `PATRQT`/`PATRQST`
mismatch above, are worth a line back to NHA, alongside
`corrections/2026-08-27-report-to-nha.md`, not a change to this file.
