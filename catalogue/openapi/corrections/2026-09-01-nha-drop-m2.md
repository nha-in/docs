# Corrections, hiecm-m2.yaml against the 2026-09-01 NHA drop

Diffed in `catalogue/openapi/nha-drops/2026-09-01-diffs/m2-linking.md`. Four
raw drop files are stored untouched under
`catalogue/openapi/.raw/nha-2026-09-01/fixed/hiecm/`
(`hip-initiated-linking.yaml`, `user-initiated-linking.yaml`,
`link-token.yaml`, `patient-share.yaml`), each hashed and recorded under
`x-abdm-sources` in `hiecm-m2.yaml`. Nothing was fixed silently; every
departure from either side is listed here.

The callback payload backfill is the priority result of this pass. Three of
`hiecm-m2.yaml`'s webhooks, `m2_on_discovery_request`, `m2_on_link_init` and
`m2_on_link_confirm`, were declared with a path and no body, a gap
`corrections/2026-08-25-m1-m2-m3-ingest.md` explicitly flagged ("declared as
webhooks with a path and no body"). The drop supplies full request payloads
for all three, transcribed below and now in the file.

## Applied, HIGH confidence

### 1. Headers attached to the 7 matched M2 path operations

None of `hiecm-m2.yaml`'s path operations referenced `RequestId`,
`Timestamp` or `CmId` before this pass, even though `components/parameters`
already defined them. Two new parameters are added, `XHipId` (`X-HIP-ID`)
and `XHiuId` (`X-HIU-ID`); neither existed before. Headers are attached only
to the 7 operations the drop actually matches, read directly off the drop's
own `parameters` block for that operation, not inferred:

- `m2_generate_link_token`: REQUEST-ID, TIMESTAMP, X-CM-ID, X-HIP-ID
- `m2_hip_link_care_context`: REQUEST-ID, TIMESTAMP, X-CM-ID, X-HIP-ID (plus the existing X-Link-Token)
- `m2_link_care_context_notify`: REQUEST-ID, TIMESTAMP, X-CM-ID, X-HIP-ID
- `m2_sms_deep_link_notify`: REQUEST-ID, TIMESTAMP, X-CM-ID
- `m2_on_discover_care_contexts`: REQUEST-ID, TIMESTAMP, X-CM-ID
- `m2_receive_link_init`: REQUEST-ID, TIMESTAMP, X-CM-ID
- `m2_receive_link_confirm`: REQUEST-ID, TIMESTAMP, X-CM-ID

The other 3 path operations in this file, `m2_consent_hip_on_notify`,
`m2_hip_health_information_on_request` and `m2_hip_data_flow_notify`, are
not covered by any of the four drop files (they belong to
`consent-management-data-flow.yaml`, out of scope for this pass), so no
headers were added to them. Inventing a header set for an operation the drop
does not document would be a guess, not a correction.

`XHiuId` is added to `components/parameters` because the drop declares it
alongside `X-HIP-ID`, but no matched M2-linking operation in this drop
carries it, so nothing in this file references it yet. It is there for the
next pass that needs it, not decorative.

### 2. `ErrorResponse.code`, `integer` corrected to `string`, and the flat 401 shape split out

NHA's own pattern, `^(ABDM-\d{4}|\d{3,6})(: )?$`, cannot be represented as
an integer; every code example in the drop and in this file's own
`x-abdm-errors` table is a string like `ABDM-1006`. `ErrorResponse.code` is
corrected to `string` with that pattern.

The drop's 401 responses use a different shape from its 400/404/500
responses: flat (`code`, `message`, `description`, no wrapping `error` key)
and carrying a `900902`-family numeric code, distinct from the `ABDM-xxxx`
family every other error response uses. Rather than force one schema to
cover both shapes, a new `FlatErrorResponse` is added and
`components/responses/Unauthorized` now points to it; `BadRequest`,
`NotFound` and the two new responses below (`InternalServerError`,
`ServiceUnavailable`) keep the wrapped `ErrorResponse` shape. A new
`Forbidden` response is added as `text/plain`, matching the drop's own
"Access Denied" plain-text 403 body on every M2-linking operation checked,
not JSON.

The trailing `": "` the pattern allows is the exact defect
`catalogue/hiecm/errors/abdm-1016.md` recorded from a live sandbox response
and that `corrections/2026-08-27-report-to-nha.md` item 4 asked NHA to
document. The drop's own schema now carries that same pattern, corroborating
that atom from a second, independent source; noted in `ErrorResponse`'s
description.

### 3. `HIType` enum, `Invoice` added

Now 8 values, not 7. The drop carries this eighth value identically across
five separate operations, not a one-off. `HIType`'s description now says so
and points at `corrections/PENDING.md` item P2, which still records seven
and cites no source; updating that entry is out of scope for this pass,
since `PENDING.md` is not one of the two files this pass may edit. Whoever
owns `PENDING.md` should read this note and update P2 to eight, citing this
drop.

### 4. Three webhook payloads populated: `m2_on_discovery_request`, `m2_on_link_init`, `m2_on_link_confirm`

Transcribed from `user-initiated-linking.yaml` operations
`abdm-user-initiated-linking 1`, `3` and `5` respectively. Each webhook
gains a `requestBody` (new schemas `DiscoveryRequestPayload`,
`LinkInitPayload`, `LinkConfirmPayload`) and the `REQUEST-ID`, `TIMESTAMP`,
`X-HIP-ID` headers the drop declares on the matching operation. The `202`
response and its description are kept as this file's primary documented
contract; the drop's own additional response codes for these three
(`400`/`401`/`403`/`500`) are not adopted here, see Deferred item 13.

Retry behaviour for these three legs is not stated anywhere in the drop or
in any of NHA's other material checked. It stays unknown; nothing was
invented.

The drop's own operation for `m2_on_link_init` (`abdm-user-initiated-linking
3`) documents this leg's success response as `200`, not `202` like every
other callback leg in the drop. That is an inconsistency in the drop itself,
not adopted here: the `202` primary contract stays as documented above.

Recorded as a new `x-abdm-sources` entry on `hiecm-m2.yaml`, `role:
upstream`, dated to this drop.

### 5. `m2_generate_link_token` corrected to async (`202`), and a new webhook `m2_on_generate_token_result`

The success response changes from a synchronous `200` carrying
`LinkTokenResponse` to `202 Accepted` with no body. The token itself now
arrives on a new webhook, `m2_on_generate_token_result`
(`/v3/hip/token/on-generate-token`), whose payload
(`OnGenerateTokenResultPayload`) carries `abhaAddress` and `linkToken` on
success or `error` on failure, always with `response.requestId`.
`LinkTokenResponse`, no longer referenced by anything in this file, is
removed; its fields live on in the new payload schema instead.

This changes the documented integration shape for link token generation. An
earlier version of this operation's description and this file's
`info.description` both now call this out explicitly, and both say plainly
that the previous synchronous `200` claim was never verified against the
sandbox. NHA's own drop documents this callback's own success response as
`200`, not `202` like the rest of this file's webhooks; recorded as the drop
states it, not normalised to match the rest, and flagged in the operation
description as worth raising with NHA.

## Applied, MEDIUM confidence

### 6. `403`, `404`, `500` (and `503` where the drop shows it) added

Across the 7 matched path operations, matching each operation's own
response set in the drop exactly rather than a uniform blanket:

- `m2_generate_link_token`: `403`, `404`, `500`, `503` (new `ServiceUnavailable` response)
- `m2_hip_link_care_context`, `m2_link_care_context_notify`, `m2_sms_deep_link_notify`: `403`, `404`, `500`
- `m2_on_discover_care_contexts`, `m2_receive_link_init`, `m2_receive_link_confirm`: `403`, `500` (no `404`, matching the drop)

### 7. Three new webhooks: `m2_on_carecontext_result`, `m2_on_context_notify_result`, `m2_on_sms_notify_result`

The result legs for `m2_hip_link_care_context`, `m2_link_care_context_notify`
and `m2_sms_deep_link_notify` respectively, transcribed from
`hip-initiated-linking.yaml` operations 2, 3 and 5. None of these three were
named in `corrections/2026-08-25-m1-m2-m3-ingest.md`'s list of missing M2
callbacks, because that note audited the M1/M2/M3 specification files, which
never modelled HIP-initiated linking as asynchronous at all. New schemas:
`OnCareContextResultPayload` (success fields or `error`, `status` kept as
free text rather than a closed enum because one of the drop's three values,
`"invalid   [invalid request]"`, reads as malformed prose rather than a wire
value), `OnContextNotifyResultPayload` and `OnSmsNotifyResultPayload`
(identical `acknowledgement.status` enum `[SUCCESS, ERRORED]` plus optional
`error` shape). All three carry `REQUEST-ID`, `TIMESTAMP`, `X-HIP-ID`
headers and echo the originating call's `REQUEST-ID` as
`response.requestId`.

### 8. `LinkCareContextNotifyRequest.notification.hip`, `name` and `type` added

The drop's own schema for this operation only bothers to define `id`'s
properties but lists `name` and `type` as required, an inconsistency in the
drop itself. `name` and `type` are added as documented string fields and
`hip.required` now lists all three, with a note in the schema description
that the drop does not say what `name` or `type` contain beyond a bare
string, so nothing further was invented. The worked example for this
operation is updated to include both, which the drop's own request example
lacked; the addition was necessary for `oas3-valid-media-example` to pass,
not merely cosmetic.

## Also applied, credited to an earlier correction

### TIMESTAMP, stale IST claim in this file's own copy corrected to UTC

`components/parameters/Timestamp` in this file still said "in IST, the
+05:30 offset" with a `+05:30` example, the exact claim
`corrections/2026-08-26-timestamp-utc.md` already corrected in
`hiecm-gateway.yaml` and the shared glossary. Because every module file is
self-contained per `CONVENTIONS.md` (no cross-file `$ref`), this file's own
copy of the parameter had never been touched by that correction. Fixed here:
description now says UTC with milliseconds and a `Z` suffix, and the example
is `2022-10-06T15:10:00.587Z`. Every `TIMESTAMP` example across all four
2026-09-01 drop files uses exactly this shape, extending that correction's
evidence from "one sandbox call, M1 only" to "every M2-linking operation NHA
itself documents in this drop," corroboration recorded in the parameter's
own description.
