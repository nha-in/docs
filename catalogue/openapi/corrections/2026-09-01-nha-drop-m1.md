`m1_enrolment_request_otp`, `m1_enrolment_verify_abdm_otp`,
`m1_enrolment_address_suggestions`, `m1_enrolment_face_auth_init`,
`m1_profile_request_otp`, `m1_profile_verify_otp`, `m1_profile_get_account`,
`m1_token_refresh`, `m1_login_select_account`, `m1_enrolment_list_children`,
`m1_benefit_get_by_abha` and `m1_benefit_get_state_district` each previously

- `SuggestionResponse` (pre-existing, but orphaned: defined in the original

- `TokenIssuanceResponse` (new: `token`, `expiresIn`, `refreshToken`,

### 2. Standard error responses added to all 35 matched operations

Every matched operation that previously documented only `200` (29 of them,
by the corrected count above) now also carries `400`, `401`, `403` and
`500`, each by `$ref` to three new shared response components,
`Forbidden`, `ServerError` and `UnprocessableEntity` (the last used only
where noted below), added alongside the existing `BadRequest`,
`Unauthorized` and `NotFound` components, all four pointing at the existing
shared `ErrorResponse` schema (`code`, `message`, `timestamp`, `details`).
The six operations that already had partial coverage got only what was
missing:

- `m1_login_request_otp` (had only `401`): added `400`, `403`, `404`,
  `500`.
- `m1_login_verify` (had `400`, `401`, `404`, `422`): added `403`, `500`.
- `m1_login_search` (had only `404`): added `400`, `401`, `403`, `500`.
- `m1_phr_search_abha_address` (had only `404`): added `400`, `401`,
  `403`, `500`.
- `m1_benefit_search_insurance` (had `400`, `401`, `500`): added `403`,
  `404`.
- `m1_benefit_link_or_delink` (had `400`, `401`): added `403`, `500`.

Four operations also picked up an extra code the drop specifically
documents, per the report's per-operation notes: `422` on
`m1_enrolment_by_aadhaar` and `m1_enrolment_by_document` (biometric and
face-auth validation failures), `404` on `m1_find_abha_search` and
`m1_benefit_search` (not-found cases). `422` was also added to
`m1_profile_verify_otp`, matching the report's note for that operation.

Only the status codes and the shared `{code, message}` error shape were
imported. The drop's own per-code prose is boilerplate reused across
unrelated operations (the report's `gateway.md` and this diff both note the
pattern), so it was not copied in; the existing `ErrorResponse` schema and
its short, generic response descriptions were reused instead.

### 3. `X-token` / `T-token` / `R-token` required, per operation

Per the task brief's own steer: the shared parameter components (`XToken`,
`TToken`, `RToken`) were left `required: false`, and nine operations where
the drop's own documented header is required got an inline per-operation
override instead:

- `X-token`, `required: true`: `m1_enrolment_list_children`,
  `m1_profile_get_account`, `m1_profile_get_abha_card`,
  `m1_profile_get_qr_code`, `m1_profile_logout`, `m1_profile_request_otp`,
  `m1_profile_verify_otp`.
- `T-token`, `required: true`: `m1_login_select_account`.
- `R-token`, `required: true`: `m1_token_refresh`.

Three operations that also carry `X-token` were deliberately left alone,
for two different reasons:

- `m1_login_verify` carries `X-token` as a parameter, but the report's
  per-operation entry for it does not tag S1 (the requiredness finding),
  meaning the drop does not mark it required there either. Left `false`,
  matching `m1_enrolment_by_aadhaar`, the one operation the report names
  explicitly as needing to stay optional.
- `m1_profile_update_account` and `m1_benefit_link_or_delink` both carry
  `X-token` in ours, but the drop omits the parameter from these two
  operations entirely rather than marking it required or optional. That is
  a documentation gap in the drop, not evidence for any particular
  `required` value, and removing a header two account-scoped operations
  plainly need is exactly what "do not adopt without confirmation" (item
  10 in the report) says not to do on this evidence alone. See "Deferred
  to sandbox".

Because `RToken` was referenced by exactly one operation before this pass,
overriding it inline there leaves the shared `RToken` component itself
unused. Spectral flags this as a warning, not an error; left as is rather
than deleting a documented, correctly-described shared parameter over one
lint warning.

## Applied, MEDIUM confidence

### 4. `Benefit-Name` vs `BENEFIT_NAME`: evidence recorded, nothing renamed

The `BenefitName` parameter's description already documented that NHA's own
Postman collection spells this header four different ways. A note was
added recording that the 2026-09-01 drop is a fifth, independent data
point: `Benefit-Name`, spelled consistently across all 7 places it appears
in that file. This does not settle which spelling is correct; the drop
disagrees with the collection's own majority spelling as much as it
confirms any one variant. The header name itself (`BENEFIT_NAME`) and its
`required: false` are unchanged. Settling this needs one real sandbox call
per spelling, per the report's own recommendation.

### 7. `dayOfBirth`, `monthOfBirth`, `yearOfBirth`, `stateCode`, `districtCode`: string to integer

On `m1_profile_update_account`'s `200` response only (not on
`m1_profile_get_account`, where the drop itself still documents these as
strings with quoted examples like `"1999"`). The drop's schema, and every
one of its examples for this operation, agree these five fields are
numeric with no internal contradiction, unlike the two fields covered
below. Each retyped property carries `x-abdm-correction: '2026-09-01-7'`.
Graded MEDIUM rather than HIGH, per the report, because it is a breaking
type change for any consumer currently parsing these as strings: called
out here explicitly. The two named response examples on this operation
that quoted `stateCode`/`districtCode` as strings (`'32'`, `'563'`) were
updated to bare integers so the examples still validate against the new
schema.

### 8. `otpSystem`, required, on two request schemas

Added to `PhrOtpRequest` (used by `m1_phr_request_otp`) and to
`m1_send_email_verification_link`'s inline request schema, both `type:
string`, `required`, matching the drop's own example value (`abdm,
aadhaar`), each carrying `x-abdm-correction: '2026-09-01-8'`. The
pre-existing named examples on both operations (`default` on the email
link operation; `mobile_otp` and `aadhaar_otp` on the PHR OTP operation)
were updated to include `otpSystem`, since Spectral validates named
examples against the schema they illustrate and a required property
missing from an example is a lint error, not just a gap.

These are the two items the task brief and the report's own audit both

### 5. `preferred`: string vs integer, `m1_enrolment_claim_abha_address`

The drop's property-level schema says `preferred` is `type: string`, but
two of the drop's own three named request examples for this exact
operation still send `preferred: 1`, a bare integer, contradicting their
own schema. This is the drop's own `payload_findings.json` audit finding,
confirmed present in the `fixed/` file this diff compares against. Ours
keeps `preferred: {type: integer}` unchanged. Settling this needs one real
sandbox call sending each type and reading which one the sandbox accepts,
exactly as the report recommends; not decided here.

### 6. `reasons`: not marked required, `m1_profile_verify_otp`

The drop's schema lists `required: [scope, authData, reasons]`, but the
drop's own `payload_findings.json` shows 6 of its own named examples for
this exact operation failing schema validation specifically because they
omit `reasons` (deactivate, delete, re-KYC, update mobile, update email,
and a password-flow example). A `required` list that the source's own
majority of examples violate is not evidence to copy in; `reasons` is more
likely required only for a subset of `purpose` values that this shared
verify endpoint's schema does not model. `reasons` stays out of `required`
on this operation, unchanged.

## Deferred to sandbox

- **Logout path, `/abha/api/v3/account/request/logout` vs
  `/abha/api/v3/profile/account/request/logout`.** The drop's path for
  `m1_profile_logout` is missing the `profile` segment every sibling path
  in the drop keeps. Everything else about the operation (summary, tag,
  headers, and the drop's own `X-token: required` finding, applied above
  under correction 3) matches ours exactly. Read as a typo in the drop,
  not a second endpoint, per the report; our path is unchanged. One real
  call against the shorter path would settle it either way.
- **`X-token` absent from the drop on `m1_profile_update_account` and
  `m1_benefit_link_or_delink`.** Covered under correction 3 above: not
  removed from either operation on the strength of an omission alone.
- **`202 Accepted` vs `200` on `m1_download_phr_card`.** The drop's success
  status for what otherwise reads as a synchronous PNG return is `202`,
  not the `200` ours documents. Same shape of claim as the `202` findings
  already raised against the gateway session and bridge-url calls in
  `gateway.md`. Left as `200`.
- **Header and path-parameter casing.** `Transaction_Id` (drop) vs
  `TRANSACTION_ID` (ours) on `m1_enrolment_address_suggestions`, and
  `abhanumber` (drop) vs `abhaNumber` (ours) as the path parameter name
  across the three benefit-by-ABHA-number lookups. The report grades this
  LOW and notes the path-parameter casing has no wire effect, since the
  literal URL segment sent is a substituted value, not the template name.
  Left as ours; worth a consistency pass the next time these operations
  are touched for another reason, not on its own.

## Follow-up, same day: two page-level defects the drop exposed

1. The primary server carried `/abha/api/v3` while every path also starts
   `/v3/`, so rendered curls doubled the segment (`/abha/api/v3/v3/...`).
   The server is now `https://abhasbx.abdm.gov.in/abha/api`. Our bug, not
   NHA's; the verified atom curls always used the single-segment URL.

   their description, which rendered on the public pages. Every response
   description now describes the response; provenance lives here, where it
   belongs. The page generator also learned to derive a response example
   from the schema, the same way it already did for requests, so a
   documented 200 renders a body rather than prose alone.
