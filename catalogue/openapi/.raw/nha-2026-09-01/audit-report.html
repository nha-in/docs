ABDM Swagger Audit

Remediation

All ten specs now validate

A corrected copy of all ten specs sits in fixed/, alongside a CHANGES.md listing every edit with its before and after. The originals are untouched and byte-identical to what the CMS serves. Eight rounds were applied: self-contradictions where only one resolution was possible; corrections backed by evidence inside the suite; and finally answers mined from the official ABDM V3 milestone documents and one live request. What the reference documents settled

Two questions that looked like judgment calls turned out to have evidence behind them, found in the official ABDM V3 milestone documents linked from the sandbox:

  • The timestamp format is yyyy-MM-dd'T'HH:mm:ss.SSS'Z'. The M2, M3 and ABHA/PHR reference documents use it exclusively — 131 occurrences of a single literal, and not one epoch or space-separated value. ABHA's 2024-05-10 11:13:04 was the sole outlier and is now converted.
  • The epoch-millis timestamps were never wrong. Every one sits inside a Spring Boot error envelope — {timestamp, path, status, error, requestId} — on a 500 response, where epoch milliseconds is the framework's own rendering. That is a different field from the ABDM protocol timestamp, and it was left alone. What looked like three competing encodings is really two correct ones plus one genuine outlier.

The required lists look wrong, not the examples. Sixteen request examples omit a field their schema marks required — but the evidence points at the schema. All six examples on /profile/account/verify omit reasons; the PATCH on /profile/account sends only the field being changed, which is what PATCH is for; and the example that omits loginHint and loginId is named "LINK or DELINK via X-token", i.e. the variant that authenticates by header instead. Filling these in would document requests nobody sends. Relaxing required is the likely fix, but that loosens a contract, so it is left open.

Resolved

The isHip/isHIP conflict was two endpoints, not one typo

The reference documents use isHIP in every /providers, /providers/{id} and /govt-programs sample, and isHip only under /bridge-service/serviceId/{serviceId}. So gateway.yaml was right for bridge-service and wrong for the other three; scan-and-pay was right all along. Three occurrences corrected, and the two specs now agree on /providers/{provider-id}. The /health-lockers response also uses isHip but no document covers it, so it was left alone.

Resolved

An official 69-code error registry exists, and the specs diverge from it

The M2 document carries an "Error Codes Listing" mapping every ABDM-xxxx to one meaning. Twelve placeholder messages — "string" and "error message" shipped as documentation — were replaced with the registry's text. But the registry also exposes how far the specs have drifted:

  • ABDM-1006 is "Bad Request, invalid request Body" — yet PHR uses it for eleven distinct validation failures ("Invalid Password", "Invalid Email Id", and so on). ABDM-1010 "Validation failed" looks like the code that was meant.
  • ABDM-1001 is "No data found" — but consent-management-data-flow documents it as "unable to connect database", which is ABDM-1000.
  • 22 codes in the specs are absent from the registry (ABDM-1065, ABDM-1103–1107, ABDM-1211, ABDM-2429, ABDM-2500 and others) — the registry appears to predate them rather than the codes being wrong.
  • The registry contradicts itself twice. ABDM-1035 is listed as both "Invalid HIP ID" and "OTP does not matched"; ABDM-1006 as both "Bad Request, invalid request Body" and "Invalid combinations of scopes".

None of the code-to-meaning divergences were changed. The specs likely document what the service really returns, and the registry is the normative list — reconciling them is ABDM's call, not a documentation edit.

Unfixable — truncated at source

The gateway JWKS is broken in the official documents too

The reference documents carry the same 142-character modulus that decodes to 106 bytes. The truncation is not a copying error in the spec — ABDM publishes it that way everywhere. A live fetch would settle it, but /certs requires credentials. No substitute key was invented: a plausible-looking but fabricated public key in a health-data specification is worse than a visibly broken one.

One tier-2 decision now looks less certain. Stripping the trailing : from 555 error codes was justified on the clean form appearing elsewhere in the suite. The reference documents complicate that: their normative registry lists every code clean, but their JSON response samples show the dirty form 294 times against 100 clean. If the service really emits "ABDM-9999: " on the wire, that change should be reverted — every edit is logged in CHANGES.md, so it is one pass to undo.

Enriched

Every error code now states its own meaning

The generic note was replaced with the code's actual definition. Where the code appears in the M2 registry the meaning comes from there (309); for the 22 newer ABDM codes and the WSO2 numeric codes the registry predates, it comes from the spec's own sibling message example (255).

What was deliberately not mined. The extraction also produced flow-specific sentences — "Request ID sent in init API call" for requestId, for instance. Accuracy beat coverage; that is why ABHA and PHR sit at 28% and 26% rather than higher.

This round also caught a regression introduced by an earlier one. The array→object unwrap left a duplicated type: object in 39 ABHA branches. Settled

hiType now has one enum, everywhere

All 33 hiType/hiTypes schemas across the four specs that carry the field now hold the identical eight values in the identical order — DiagnosticReport, DischargeSummary, HealthDocumentRecord, ImmunizationRecord, OPConsultation, Prescription, WellnessRecord, Invoice. Two occurrences that had no enum at all now have one, one spec's list had DiagnosticReports plural, and two examples used an uppercase spelling.

This one nearly went wrong. The reference documents use an uppercase vocabulary in the care-context linking samples and carry a server error reading "Invalid HIType, it must be in PRESCRIPTION, DIAGNOSTIC REPORT, OPCONSULTATION…" — seven values, no Invoice. That read convincingly as a second vocabulary belonging to the linking endpoints, and the two enum-less occurrences sat on exactly those endpoints. It was wrong: the camelCase set is the real vocabulary throughout and the uppercase forms in the documents are stale. Suggestive evidence is not the same as correct evidence.

Still open. The ABDM-1006/ABDM-9999 overloading; the curve25519 contradiction; the bodies on 204; the sixteen over-strict required lists; three ABHA 400 examples that are arrays where the schema says object; and four codes that cram several values into one string. Each needs a decision from whoever owns the service.

Start here

Two of the ten files fail to parse at all

Before any of the consistency questions matter: abha-api-v3.yaml and phr-api.yaml are not loadable YAML. Four lines contain unquoted template placeholders that YAML reads as flow mappings with an unhashable key. Swagger UI's browser parser is lenient enough to render them; strict loaders (PyYAML, snakeyaml, most codegen toolchains) stop dead.

Blocking

Unquoted {{…}} placeholders break the YAML parse

abha/abha-api-v3.yaml:1594, :1597  ·  phr/phr-api.yaml:10209, :10235

# abha-api-v3.yaml:1594 — the {{ }} has already been mangled into explicit-key syntax
example: { ? { txnId } }        ← ConstructorError: found unhashable key

# phr-api.yaml:10209
example: {{profile-photo}}      ← same failure

# the fix is one pair of quotes:
example: '{{txnId}}'

This is an inconsistency, not a convention: ABHA quotes 305 of its 308 placeholders, PHR quotes 68 of 171. The remaining bare ones are simply oversights. All eight HIE-CM specs parse clean and contain no placeholders at all.

Question one

Timestamps

The TIMESTAMP request header is consistent everywhere. The timestamp field inside response bodies is not — it is encoded three mutually incompatible ways, and a client that parses one family's format will fail on the other two.

The header is fine

All nine specs that define the TIMESTAMP header use RFC 3339 with milliseconds and a Z suffix. Eight HIE-CM specs share the frozen example 2022-10-06T15:10:00.587Z; PHR uses 2024-09-03T11:20:51.456Z. ABHA is the odd one out only in that it ships the Postman variable {{$isoTimestamp}} rather than a literal — same format, different presentation.

The body field is not

Contradiction

Eight fields declare format: date-time but give a non-RFC-3339 example

abha-api-v3 — enrolment and profile error responses

2024-05-10 11:13:04 has a space where RFC 3339 requires T, and carries no timezone at all. A generated client that parses the declared date-time format rejects the documented example. This is the same field the spec elsewhere types as a plain string, so validation strictness decides whether it breaks.

Type drift

The same concept is typed string in 80 places and number in 29

Across the suite, 72 timestamp-ish schemas are type: string with no format, 8 are string + date-time, and 29 are type: number. There is no rule that predicts which — subscription and user-initiated-linking chose epoch millis while their sibling HIE-CM specs chose strings.

Cosmetic

Three ABHA timestamps are unquoted and silently become dates

abha-api-v3 — 400 responses on the enrolment endpoints

YAML 1.1 resolves bare 2024-05-10 12:01:22 to a native timestamp, so a loader hands the tool a date object where the schema promised a string. Quoting them restores the declared type.

One place gets it right. consent-management-data-flow documents dhPublicKey.expiry with both an RFC 3339 example and an explicit format string in the description — yyyy-MM-dd'T'HH:mm:ss.SSS'Z'. That pattern, applied suite-wide, is the fix.

Interop risk

The same code carries different meanings in different specs

Ten of the 42 distinct error codes have divergent message text. Two are severe enough to defeat code-based branching:

  • ABDM-9999 — documented with 21 different messages. It is "Unknown exception" in gateway and hip-initiated-linking, but PHR uses it as a general validation error ("Invalid Scope", "Invalid OTP Value", "Invalid Month Of Birth", "This ABHA Address already exists"), and subscription uses it for business-rule failures ("To date should be present or future date").
  • ABDM-1006 — 12 meanings. "Bad Request, invalid request Body" in HIE-CM, but "Invalid Password", "Invalid Email Id", "Invalid Mobile Number" and others in PHR, and "Invalid X-token" in ABHA.
  • ABDM-1001 — "No data found" in four specs, but "unable to connect database" in consent-management-data-flow.
  • 900901 — "Invalid Credentials" in seven specs, "Unauthorized" in one.

Placeholder text also survived into published examples: ABDM-1001 is documented as "error message" in two specs, and ABDM-9999 as the literal string "string" in patient-share.

Question three

Encryption key APIs

Two endpoints publish key material, in two unrelated formats. ABHA's is a genuine, verifiable RSA key. The gateway's JWKS example is truncated to the point of being unusable, and the ECDH key material in the data-flow spec contradicts the curve it declares.

Verified good

ABHA's published key is real

The publicKey example decodes from 736 base64 characters to 550 bytes and loads cleanly as a SubjectPublicKeyInfo structure containing a 4096-bit RSA public key. The companion encryptionAlgorithm field documents RSA/ECB/OAEPWithSHA-1AndMGF1Padding — worth noting that this is SHA-1-based OAEP, a legacy padding choice, but it is at least stated explicitly and consistently.

Unusable example

The gateway JWKS modulus and certificate are both cut off mid-value

hiecm/gateway.yaml — GET /api/hiecm/gateway/v3/certs, 200 response

# n — the RSA modulus
142 base64url chars → 106 bytes → an 848-bit modulus
a 2048-bit RSA key needs 256 bytes / ~342 chars

# x5c[0] — the X.509 certificate
173 base64 chars → not decodable at all
(length ≡ 1 mod 4 — invalid base64, truncated mid-character)

# e is fine
'AQAB' → 65537 ✓

Anyone copying this example into a test fixture gets key material that no JOSE library will load. The truncation looks like a display-width trim applied when the example was authored.

Contradiction

The ECDH key example doesn't match the curve the spec declares

hiecm/consent-management-data-flow.yaml — keyMaterial.dhPublicKey.keyValue

The schema states cryptoAlg: ECDH and curve: curve25519. A Curve25519 public key is 32 raw bytes. The example decodes to 65 bytes beginning with 0x04 — the SEC1 uncompressed-point encoding used by the NIST curves:

BFN7KTdOT0jIAExG2A8Jg+01wMPWxptiGqwHRVvtiVEsUq2FR7P2UdqZxJyPJSeR6muai21iQhasNxnhh8I5M+g=
  ↓ 65 bytes, first byte 0x04
  parses as X25519 public key ....... No  (must be 32 bytes)
  parses as a P-256 point ........... No  (point not on the curve)

So the example is neither a valid key on the declared curve nor a valid key on the curve its encoding implies. This is the single field that governs how health records are encrypted in transit between HIP and HIU — it is the one that most needs an example an implementer can trust.

Schema bug

ABHA's certificate endpoint has an indentation error that invents a field

abha/abha-api-v3.yaml — /abha/api/v3/profile/public/certificate, 401 response

The example: keyword sits one level too deep and lands inside properties, so the 401 body is documented as having a third field literally named example. The same response also disagrees with itself: the schema gives code: "900902" while the examples block gives "900902 " with a trailing space. It is the only occurrence of this indentation bug in the suite.

Protocol

All ten gateway operations attach a response body to 204 No Content

hiecm/gateway.yaml — including /certs and /sessions

Each 204 declares an application/json body carrying {error: {code: 'ABDM-1001: ', message: 'No data found'}}. A 204 must not have a body; most HTTP clients discard it unread, so the documented error never reaches the caller.

Documentation gap

Copy-paste noise in the crypto fields

cryptoAlg is exampled as both ECDH and ECDH.; parameters as both Ephemeral public key and Ephemeral public key. — the description's trailing period pulled into the value. Several occurrences of keyMaterial, curve, keyValue and nonce carry no example at all, so the three operations that exchange key material are documented to different depths.

Field renamed

The same provider lookup returns isHip or isHIP depending on which spec you read

GET /api/hiecm/gateway/v3/providers/{provider-id} — in both gateway and scan-and-pay

gateway documents {facilityType, identifier, isHip}. scan-and-pay documents {facilityType, identifier, isHIP, isPaymentShare, isRecordShare, scanPayVersion}. JSON keys are case-sensitive, so at most one of these is correct.

Header naming

Three spellings of one header, and two casings of another

  • ABHA declares the same benefit header as BENEFIT NAME (with a literal space, which is not a legal HTTP field name), BENEFIT_NAME, and Benefit-Name.
  • Both ABHA and PHR declare X-Token and X-token as separate parameters. HTTP treats them as one header; OpenAPI tooling treats them as two.
  • PHR's X-Token example begins with a leading space before the JWT.
  • X-HIU-ID is exampled as IN2810014366 in four specs but as the placeholder HIU_ID in patient-share.
Breaks codegen

Duplicate operationId values in three specs

scan-and-pay reuses patient-share 2 six times, abdm-patient-share 1 and scan-gateway 2 four times each. consent-management-data-flow has six duplicated IDs, subscription one. Most generators either fail or silently collapse the colliding methods.

How this was checked

All ten specs were loaded with a YAML parser that quotes unparseable placeholder scalars and records each repair, so the two failing files could be analysed alongside the eight that parse. Every example was then validated against the schema node it sits on (type, format, enum, pattern, length), and every media-type example and examples[*].value against its full schema using JSON Schema draft-7, with OpenAPI 3.0 nullable translated to a union type. Placeholder strings of the form {{…}} were excluded from type and format checks. Key material was decoded and loaded with a real cryptography library rather than pattern-matched — that is how the ABHA key was confirmed genuine and the gateway's confirmed truncated.
