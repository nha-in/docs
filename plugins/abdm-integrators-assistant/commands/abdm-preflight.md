Check the preconditions for `$ARGUMENTS` before building anything. With no argument, check what every module needs.

Each item below fails in a way that is reported as something else, which is why they are checked first rather than diagnosed later.

## Every module

- **The clock.** `TIMESTAMP` in UTC, with milliseconds and a trailing `Z`. Local time is refused, sometimes as a 404 on a path that is correct.
- **A fresh REQUEST-ID per call**, generated by you and logged before sending. A reused one is refused, and once a call has failed it is the only handle on it.
- **The gateway session token**, in `Authorization: Bearer`. A numeric code with a `description` field means this is wrong or expired.
- **`X-CM-ID`** set for the environment you are calling.

## M1, and every module that encrypts

- **The certificate**, fetched rather than pinned from a sample. It arrives as base64 DER, so add PEM armour before your library will load it.
- **The padding proved, not assumed.** Run `/abdm-prove-encryption` first. A wrong padding is reported as a wrong value.
- **The two tokens kept apart.** The gateway token goes in `Authorization`; the user token from an enrolment or login goes in `X-token`. Profile endpoints need both.

## M2 and M3

- **A facility registered in the role you are acting in**, HIP for M2 and HIU for M3. No registration, no callbacks.
- **A reachable callback URL**, on the public internet, that you can watch while you test. Most of M2 and M3 is answered asynchronously, so a flow that looks stuck is usually a callback you never received.
- **A link token per patient** for M2, validated before use rather than assumed live.

## M4

- **An HPID before a facility.** Facility onboarding needs an HPR token, which needs a person who already holds an HPID.
- **The NHPR certificate and its own padding**, which are not M1's. Do not reuse an M1 encryption path here.

## Output

One line per item: what was checked, and what was observed. Name anything you could not check rather than passing it silently.
