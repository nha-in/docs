# Module 7.8: the ClaimResponse reader

Purpose: turn every payer answer on a pre-auth, enhancement, claim or predetermination thread into leg state: status, `preauth_ref`, amounts, item verdicts, the desk's remarks, the in-band query. Acknowledgement first, decision later, on one correlation id.

Skills: `nhcx-preauth` (the pre-auth, enhancement and predetermination answers) and `nhcx-claim` (the claim answers). One parser and one status rule for both.

## Depends on

7.1 to 7.3, 7.7.

## Inputs

- `references/fhir-knowledge.md` section 6
- `references/flow-knowledge.md` sections 2 and 3 (the payer's ids; where `preAuthRef` arrives)
- Payer answers: `nhcx-package/fhir/C5/*.json` (pre-auth and enhancement), `nhcx-package/fhir/C7/*.json` (claim), `nhcx-package/fhir/C11/predetermination-response.json`. Most generic answers have a `-pmjay` twin.

## Build

### The parser

`parse_claim_response(bundle) -> parsed`: `use`, `outcome`, the claim-level `adjudication` entry with category `status` and its `reason.coding.code`, `preAuthRef`, `identifier[0].value` (your claim number echoed), `total[]` by category (`benefit`, `eligible`, `submitted`, and PMJAY's `tax`, `incentive`), `item[]` each with its adjudications by category (`eligible`, `status`, `reason` kept verbatim, `eligpercent`, `eligquant`, `deductible`), `processNote[].text`.

### The status rule

`verdict_status(parsed) -> status`, copied exactly: `outcome queued` or reason `submitted` is `submitting`; reason `cancelled` is `rejected`; reason `queried` is `queried`; `outcome error` is `rejected`; `outcome partial` is `partial` only with reason `approved`, else `queried`; `outcome complete` is `approved` with reason `approved` or none, else `queried`. Never read `outcome` alone.

### Apply

`apply_preauth(row, parsed, envelope)` and `apply_claim(...)`: set status from the rule; keep `preauth_ref` (never overwrite a value with an empty one; PMJAY's enhancement acknowledgement carries none); set `eligible_amount`, `submitted_amount`, `items_json`, `query_note` (the item `reason` remarks and process notes, verbatim, for a `resubmit` payer's in-band query); `answered_at`; `response_json`. Set `thread_correlation_id` to the envelope's correlation id: the payer has now answered on this thread. On `queued` do nothing but record; the leg stays `submitting`.

Branch on `x-hcx-workflow_id` only to label the timeline (20 received, 21 approved, 22 enhancement approved, 23 rejected, 24 queried, 25, 26, 27, 291); the state comes from the bundle. The SHA answered an enhancement with 21; the table is a label, not a truth.

### Predetermination

The same parser; `apply_predetermination` stores the quote on `claim_predetermination` and changes nothing on the pre-auth.

## Rules

- Never close a thread on the first reply.
- `preauth_ref` is what the payer service desk wants; the bare number ends the path form.
- The desk's remarks are pipe-delimited `USER~datetime~type~comment~trust`; keep them verbatim, split them only for display.

## Validate

- [ ] The parser on every payer answer named above returns without error and yields `outcome` and `identifier`.
- [ ] `verdict_status` on the `received` answers (`C5-received-wf20`, `C7-received-wf25`) is `submitting`; on `approved` (`C5-approved-wf21`, `C7-approved-wf26`) is `approved`; on `rejected` (`C5-rejected-wf23`, `C7-rejected-wf291`) is `rejected`; on `queried` (`C5-queried-wf24`, `C7-queried-wf27`) is `queried`.
- [ ] After a 20 then a 21 on one correlation id, the leg is `approved` and `preauth_ref` holds the 20's path form or the 21's bare number, never empty.
- [ ] After a 20 on an enhancement with no `preAuthRef`, the parent's `preauth_ref` survives.
- [ ] `total[]` is read by category, not position: `C5/preauth-queried.json`, with `eligible` before `benefit`, still yields the right amounts.
- [ ] A queried answer on a `resubmit` payer fills `query_note` with the item remarks verbatim.

## Tests

- One test per answer family, asserting the status word and the amounts.
- The acknowledgement-then-decision sequence.
- C-series rows from the matrix as readers.

## Pseudo code

Parser, `verdict_status` and `apply_claim_response`: `fhir/FHIR.md` section 5. Wiring:

```
APPLY["claim_preauth"] = function (pa, env):
    p = fhir.parse_claim_response(env.fhir)
    if p.outcome == "queued" or p.status_reason == "submitted":            # the acknowledgement (20 / 25)
        if p.preauth_ref: update(pa, {preauth_ref: p.preauth_ref})
        update(pa, {thread_correlation_id: env.jwe_headers["x-hcx-correlation_id"], response_json: env.fhir}); return   # still submitting; do not close
    fhir.apply_claim_response(pa, p, env); save(pa)
    timeline_label = LABELS.get(env.jwe_headers["x-hcx-workflow_id"])    # 20 received, 21 approved, 22, 23, 24 ...; a label, not the truth

APPLY["claim_submission"] = same shape, reading 25 / 26 / 27 / 291
APPLY["claim_predetermination"] = function (q, env): p = fhir.parse_claim_response(env.fhir); update(q, {status: verdict_status(p), items_json: p.items, eligible_amount: p.totals.eligible or p.totals.benefit, response_json: env.fhir})   # nothing else changes
```
