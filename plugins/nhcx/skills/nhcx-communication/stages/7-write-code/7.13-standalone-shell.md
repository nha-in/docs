# Module 7.13: the standalone shell

Standalone mode only. Purpose: the minimum hospital system around the claims desk, so every fact the bundles need has a home and a screen to capture it. In `integrate` mode this module is skipped; the HMIS is the shell.

Skills: the foundation (`core/FOUNDATION.md`), standalone mode only. Built by the first skill that needs a patient or an admission to link.

## Depends on

7.2 (schema), 7.12 (screen conventions). Build it early enough that 7.4 has a patient to link; the plan (stage 6) says when.

## Inputs

- `nhcx-build/3-discovery.md`, standalone section
- The package pins the seed reads: `nhcx-package/fhir/B1/validation.json` and `B1/B1-check.json` (member ids), `nhcx-package/fhir/B3/preauth-request.json` and `B3/B3-request.json` (HPINs, the facility HFR id)

## Build

### Tables

| Table | Holds |
| --- | --- |
| `patient` | MRN, name, gender, date of birth, phone, ABHA number, address, photo |
| `encounter` | admission time, discharge time, ward, bed, admitting practitioner, status, discharge mode (`normal`, `lama`, `dama`, `death`), discharge stage (`before`, `during`, `after` surgery), surgery time, death time |
| `practitioner` | name, HPIN (HPR id), licence number, qualification, specialty |
| `diagnosis` | encounter, ICD-10 code, display |
| `document` | patient or encounter, bytes or pointer, content type, title |
| `settings` | facility HFR id, name, phone, participant code, the transport's settings (`own`: client id and secret, private key file; `adapter`: its URL and key), cases directory |

### Screens

Register a patient; admit; record diagnoses; upload a document; discharge (with mode, stage, times); practitioners; settings. In the same style as 7.12.

### The run script and seed

One command starts the app on a configured port, ready within forty seconds, resetting and seeding the database first when asked. The seed creates one facility, two practitioners with HPINs, and two patients with member ids. Take every id from the package pins: the member ids in `nhcx-package/fhir/B1/validation.json` and `nhcx-package/fhir/B1/B1-check.json`, the HPINs in `nhcx-package/fhir/B3/preauth-request.json` and `nhcx-package/fhir/B3/B3-request.json`. Never invent one.

### The CLI (optional)

If the plan says so, an executable that prints one JSON object per command: `token` (the ABDM session token the transport holds), `policies`, `eligibility`, `preauth`, `claim`, `task cancel`, each returning the exchange's receipt plus `correlation_id`. It calls the same functions the screens call.

## Rules

- Python standard library only, unless stage 1 chose otherwise. The standard library is enough.
- The shell holds nothing the exchange returns. Demographics from the payer live on the episode, not on `patient`, unless the user links them.
- Content types on upload are restricted to pdf, jpg, jpeg, png.

## Validate

- [ ] The run script starts the app and the port accepts connections within forty seconds.
- [ ] A seeded practitioner has an HPIN.
- [ ] A discharge can be recorded as `death` with a death time, and as `lama` with a stage.
- [ ] An upload with content type `text/plain` is refused.
- [ ] Settings hold the facility HFR id and the participant code, and 7.1 reads them.

## Tests

- Start, seed, register, admit, discharge, through the screens or the functions behind them.
