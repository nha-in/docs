# Module 7.12: screens

Purpose: the screens in `screens.json`, built the way the target builds screens, every value derived from a stored message, plus the JSON state address a driver reads.

Skills: the foundation (`core/FOUNDATION.md`) builds the case screen shell: all eight tabs, the status line, the state address, the page-load polls, the cases list. Each skill fills its own tabs and screens, and adds its legs to the state address.

## Depends on

7.1 to 7.11. Screens come last because they render what the readers stored.

## Inputs

- `nhcx-build/5-screen-plan.md`, `nhcx-build/screens.json`
- `nhcx-build/3-discovery.md` (screen conventions, helpers, styling)
- `nhcx-package/docs/03-Building a Provider/09-UI Guide.md`
- `ui/UI-GUIDE.md` for the route shape, the state address and the helper vocabulary; two or three route modules of the target for its conventions

## Build

### The case screen walks the flow

Tabs in the order and with the labels of `flow.json` `tabs`; the Pre-authorisation tab appears once the verdict is `eligible`. Above the tabs the status line and the actions from 7.11. Each step F1 to F13 has its control on the tab the flow names, offered only when the step's `holds` hold. The page-load polls run in the order `flow.json` `page_load_polls` gives, bounded, before rendering.

### Every screen in `screens.json`

For each screen: the route, the handler, the render. Each value in the screen's `values` list is rendered from the element it names; the empty state is what shows before the message arrived. A decision-bearing value with no message renders as waiting. There is no status control anywhere.

### The case screen

The timeline: one row per leg row and per archived message, in time order, with direction, path, workflow id label (7.8's labels), status word, and the payer's words verbatim (`disposition`, item remarks, process notes, `x-hcx-error_details` on a refusal). The actions open now are `next_actions` from 7.11, rendered as buttons that post to the senders; the first action is highlighted. Each pane (cover, plan, lines, forms, documents, pre-auth, communication, claim, payments) shows only when its leg exists.

### The JSON state address

`GET <case route>/state` returns everything the case screen shows, as JSON, after the same polls the screen runs: stage, sub-stage, next actions, each leg's status and ids, the inbox items, the payments. Stage 10's drivers read this.

### Polling on the request path

Where there is no worker, the case screen and the state address run 7.3's poll fallback for any leg that is `submitting` or `checking` before rendering. Bound it: one poll per leg per request, a short timeout, and never a send.

### Standalone mode

Also the capture screens from 7.13, in the same style.

## Rules

- No screen shows a decision the exchange has not sent.
- Nothing the exchange already knows is typed. Rates, payer names, `preAuthRef`, the approved amount, the UTR and the payer's wording are rendered, never fields.
- An unknown case is a 404, never an invented page.
- Screens answer within two seconds; the poll is bounded.
- Forms post and the page re-renders; no client-side rendering is needed.

## Validate

- [ ] The case page's tabs are the eight of `flow.json`, in order, with those labels (string test on the HTML).
- [ ] Every step of `flow.json` with a `routes` entry answers on that route (or the plan's equivalent recorded in `screens.json`).
- [ ] Every route in `screens.json` answers 200 for a seeded case and 404 for an unknown one.
- [ ] A case with a pre-auth `submitting` and no answer renders "waiting" (or the plan's word) and neither "approved" nor "rejected" appears on the page.
- [ ] After a 21 is applied (`nhcx-package/fhir/C5/C5-approved-wf21.json`), the page shows its `preAuthRef` and approved amount verbatim.
- [ ] After a payment notice is applied (`nhcx-package/fhir/C9/C9-notice-wf30.json`), the payments screen shows its UTR verbatim.
- [ ] After a query is applied, the inbox shows the request's `contentString` text verbatim.
- [ ] No `<input>` or `<select>` on any screen is named for a rate, a payer name, a `preAuthRef`, a UTR or a status.
- [ ] The state address returns `stage`, `sub_stage`, `next_actions` and a `legs` object, and agrees with the page.
- [ ] Every page renders within two seconds with the 7.1 stub in place.

## Tests

## Pseudo code

Layouts, per-screen values and the rendering rules: `ui/UI-GUIDE.md`. Wiring:

```
route GET  /claims                      -> index()
route GET  /claims/new                  -> new()            ; POST /claims -> create()
route GET  /claims/<id>                 -> detail()
route GET  /claims/<id>/state           -> state()          # JSON
route POST /claims/<id>/check           -> run_check + redirect
route POST /claims/<id>/plan            -> request_plan + redirect
route POST /claims/<id>/lines ...       -> add_line / save_quantities / remove_line
route POST /claims/<id>/forms           -> save_answers
route POST /claims/<id>/documents ...   -> upload / remove
route POST /claims/<id>/auth            -> ensure_auth_requirements
route POST /claims/<id>/submit          -> submit_preauth ; /cancel ; /predetermination ; /status ; /reprocess ; /release
route POST /claims/<id>/queries/<qid>/reply -> answer_query ; /acknowledge -> acknowledge_notification
route POST /claims/<id>/discharge       -> save_discharge ; /claim -> submit_claim ; /claim/documents
route POST /claims/<id>/payments/<pid>/ack -> acknowledge_payment
route GET  /claims/inbox, /claims/payments

function detail(request, id):
    row = claim(id) or return 404
    poll_all(row)                                                # bounded: one poll per submitting/checking leg, short timeout, never a send
    (stage, sub) = (row.stage, row.sub_stage)                    # stamped; never computed on a form value
    actions = next_actions(id)
    panes = [cover_pane(row), plan_pane(row) if row.plan_id else null, lines_pane(row), forms_pane(row), documents_pane(row),
             preauth_pane(row) if preauth(id) else null, communication_pane(row) if queries(id) else null,
             claim_pane(row) if preauth(id) and preauth(id).status in ("approved", "partial") else null, payments_pane(row) if payments(id) else null]
    return page(title = row.claim_no, body = stack(status_line(row, stage, sub, actions), timeline(row), tabs(compact(panes))))

function preauth_pane(row):
    pa = preauth(row.id)
    if pa.status == "submitting": verdict = muted("waiting for the payer, " + humanise(now() - pa.sent_at))
    else: verdict = dl([("Decision", pa.status), ("Payer reference", pa.preauth_ref or ""), ("Approved amount", inr(pa.approved_amount)),
                        ("Payer's words", pa.query_note or "")])                   # text, never inputs
    flags = [alert(pa.error_message, tone = "warn")] if pa.error_message else []   # a door refusal is a flag beside the state
    reply = reply_form(row.id, "preauth") if pa.status == "queried" and for_claim(row).query_mode == "resubmit" else ""
    return card("Pre-authorisation", stack(*flags, verdict, item_verdicts_table(pa), reply, cancel_form(row.id, pa)))

function state(request, id):
    row = claim(id) or return 404; poll_all(row)
    return json({stage: row.stage, sub_stage: row.sub_stage, next_actions: next_actions(id),
                 legs: {coverage: leg_json(row), preauth: leg_json(preauth(id)), claim: leg_json(submission(id)), enquiries: [leg_json(e) for e in enquiries(id)]},
                 queries: [q_json(q) for q in queries(id)], payments: [p_json(p) for p in payments(id)], documents: [d_json(d) for d in documents(id)]})

function leg_json(leg): return null if not leg else {status: leg.status, submission_kind: leg.submission_kind, workflow_id: leg.workflow_id,
        txn_id: leg.txn_id, correlation_id: leg.correlation_id, thread_correlation_id: leg.thread_correlation_id, preauth_ref: leg.preauth_ref,
        approved_amount: leg.approved_amount, eligible_amount: leg.eligible_amount, error: leg.error_message, sent_at: leg.sent_at, answered_at: leg.answered_at}
```
