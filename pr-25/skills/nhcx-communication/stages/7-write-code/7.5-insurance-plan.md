# Module 7.5: the insurance plan

Purpose: fetch the payer's package master once per facility and policy, flatten it into queryable rows, reuse it across episodes, and quote lines from it. Every package code, rate, tier, document requirement and questionnaire the rest of the build uses comes from here.

Skills: `nhcx-insurance`, whole.

## Depends on

7.1 to 7.4.

## Inputs

- `nhcx-build/mapping.json` `tables.claim_plan*`, `tables.claim_line`
- `references/fhir-knowledge.md` section 4
- `references/flow-knowledge.md` section 5 ("One plan per facility and policy", "Tiers are modifiers")
- Pin: `nhcx-package/fhir/B2/insurance-plan-request.json`; answers: `nhcx-package/fhir/C4/C4-response-pmjay.json` (package-based, PMJAY) and `nhcx-package/fhir/C4/C4-response-generic.json` (coverage-based, generic payer)

## Build

### The request builder

`build_plan_request(case_id, policy_code, provider_id) -> bundle`: a TaskBundle with one Task at `https://nhcx.abdm.gov.in/insurance/request`, `status requested`, `intent order`, `code poll`, inputs `policyNumber` and `providerId`. No id, no timestamp, no requester. Bundle id `insurance-request-generic`. Workflow id = the case number.

### Reuse before request

Before sending, look for a `claim_plan` with status `ready` for the same policy code, provider id and payer. If found, copy its id onto the episode and do not send. Only ask the payer when nothing is held or the user asks to refresh. PMJAY answers a second request while one is open with PAYR-1406.

### The parser

`parse_plan_bundle(bundle) -> {plan, benefits[], forms[]}`, reading both published shapes and merging on package code:

- `plan[].specificCost[].category` (specialty) then `benefit[].type` (package) then `cost[]`: `Procedure` is the rate; `Stratification` and `Implant` are extras named by `qualifiers[0]`.
- `coverage[].benefit[].limit[]`: the limit coded as the package is the rate; the rest are tiers.
- Extensions matched by squashed url family: `Claim-Condition` children are conditions (`ProcedureType`, `IsDayCare`, ...); `Claim-SupportingInfoRequirement` children are one requirement per document with `category`, `code`, `documentationUrl`. Requirements on the InsurancePlan itself are policy-wide.
- One `Questionnaire` per url; `/questionnaire/` is a policy form, `/stgquestionnaire/` a treatment guideline. Questions are on `item.prefix` more often than `item.text`.

Store: one `claim_plan` row, one `claim_plan_benefit` per package, one `claim_plan_form` per url. Refetching replaces all three. Keep the raw bundle in the archive; keep `response_json` on the row only if 7.2 chose a column that holds it.

### Lines from the plan

`add_line(claim_id, kind, code, parent_code)`: a procedure or implant is a line at the plan's rate; a ward or ICU tier is a line with `parent_code` = its procedure, and it rides on the procedure's `Claim.item.modifier` when the bundle is built. Quantity is an integer. The rate is the plan's; the line's `unit_price` is not editable on any screen. `lines_total` is the sum of amounts.

## Rules

- Prices come from the plan, never from a form and never from the HMIS charge master.
- The master is keyed on policy code, provider id and payer. A facility empanelled under two policies holds two masters.
- A master can be tens of megabytes; the validator (`references/fhir-knowledge.md` section 11) cannot check it whole.

## Validate

- [ ] The request builder fed the pin's data produces `nhcx-package/fhir/B2/insurance-plan-request.json` byte for byte (`created` excluded; this bundle has none).
- [ ] The parser fed `nhcx-package/fhir/C4/C4-response-pmjay.json` yields benefits with a non-empty rate, at least one requirement with a code and a `documentationUrl`, and forms keyed by url with questions.
- [ ] A second episode on the same policy, provider and payer reuses the plan with zero sends (assert with the 7.1 stub).
- [ ] A tier line carries `parent_code`; a procedure line does not.
- [ ] `unit_price` on a line equals the plan's rate for that code.

## Pseudo code

Builder and parser: `fhir/FHIR.md` section 3. Orchestration:

```
function request_plan(claim_id, refresh = false):
    row = claim(claim_id)
    if not refresh and reuse_plan(claim_id): return
    plan = insert("claim_plan", {policy_code: row.policy_code, provider_id: settings.facility.hfr_id, payer_code: row.payer_code, status: "fetching"})
    bundle = fhir.build_plan_request(row.policy_code, settings.facility.hfr_id)
    r = transport.send("v1/insuranceplan/request", bundle, recipient_of(row), workflow_id = row.claim_no, claim_no = row.claim_no, usecase = "insuranceplan")
    update(plan, {txn_id: r.txn_id, correlation_id: r.correlation_id, api_call_id: r.api_call_id, sent_at: now()})
    update(row, {plan_id: plan.id})

function reuse_plan(claim_id):
    row = claim(claim_id)
    held = select_one("claim_plan", where = {policy_code: row.policy_code, provider_id: settings.facility.hfr_id, payer_code: row.payer_code, status: "ready"}, order = "fetched_at desc")
    if not held: return false
    update(row, {plan_id: held.id}); return true                 # zero sends

APPLY["claim_plan"] = function (plan, env):
    p = fhir.parse_plan_bundle(env.fhir)
    delete("claim_plan_benefit", where = {plan_id: plan.id}); delete("claim_plan_form", where = {plan_id: plan.id})
    for b in p.benefits: insert("claim_plan_benefit", {plan_id: plan.id, code: b.code, display: b.display, category_code: b.specialty.code,
                                category_display: b.specialty.display, rate: b.rate, kind: b.kind, conditions_json: b.conditions,
                                extras_json: b.extras, supporting_info_json: b.requirements})
    for f in p.forms: insert("claim_plan_form", {plan_id: plan.id, url: f.url, title: f.title, kind: f.kind, questions_json: f.questions})
    update(plan, {status: "ready" if p.benefits else "empty", name: p.plan.name, policy_requirements_json: p.policy_requirements,
                  benefit_count: len(p.benefits), form_count: len(p.forms), fetched_at: now(), answered_at: now()})
    # the raw bundle stays in the archive; store response_json only if the column can hold tens of MB

function add_line(claim_id, kind, code, parent_code = ""):
    plan = plan_for(claim_id); b = select_one("claim_plan_benefit", where = {plan_id: plan.id, code: code})
    if kind == "tier":
        parent = select_one("claim_plan_benefit", where = {plan_id: plan.id, code: parent_code})
        extra = first(x for x in parent.extras_json if x.code == code)
        insert("claim_line", {claim_id, kind: "tier", code, display: extra.display, parent_code, quantity: 1, unit_price: extra.amount, amount: extra.amount})
    else:
        insert("claim_line", {claim_id, kind: "implant" if b.kind == "Implant" else "procedure", code, display: b.display,
                              category_code: b.category_code, category_display: b.category_display, quantity: 1, unit_price: b.rate, amount: b.rate})

function save_quantities(claim_id, quantities):                 # {line_id: n}
    for (line_id, n) in quantities: line = line(line_id); update(line, {quantity: int(n), amount: line.unit_price * int(n)})   # unit_price never changes here
```
